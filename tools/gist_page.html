Reverse engineering · DJI Osmo 360

Decoding the .OSV dual-fisheye format

DJI's Osmo 360 records a proprietary file only DJI Studio will stitch. Here is the container, the per-unit calibration, the lens model read from DJI's binary, and a pure-Python path from one .OSV to an 8K equirectangular 360 — every number taken from the file, so it generalises across camera units.

2× HEVC 3840² 10-bit f-theta lens, 5+2 terms format decode libav-free output 7680×3840

01The container

.OSV is a plain MP4. It holds eight tracks — two raw fisheye videos, audio, four DJI metadata/debug tracks, and a thumbnail:

#kindcodecwhat it is
0,1videoHEVC Main10the two fisheyes, 3840×3840, 10-bit, >180° each
2audioAACstereo 48 kHz (a 16-bit PCM .WAV sits alongside)
3datadjmdcalibration + per-frame orientation — the useful one
4datadjmdper-frame exposure / white-balance telemetry
5,6datadbgisensor debug (OmniVision OV68A40); not needed
7videoMJPEG688×344 thumbnail

An MP4 is a tree of boxes; a track's samples are located through its sample tables. That is all pure Python — no codec — so the whole format, including DJI's metadata, reads with no ffmpeg at all. Only the HEVC pixels need a decoder, and that is libavcodec in-process, never the binary.

02The metadata — per-unit calibration

Track 3's samples are protobuf. Sample 0 is a header carrying this specific camera's factory calibration; every later sample carries that frame's orientation. Field numbers survive in the wire format even without the schema; the names are ours.

Calibration block 2.6.<n>

fieldmeaning
.1 .2 .3 .4fx fy cx cy — focal length, principal point
.5 .6 .7 .8radial distortion k1 k2 k3 k4
.15radial distortion k5 — stored apart from k1..k4
.20tangential distortion p1 p2
.12 .13 .14extrinsic yaw / pitch / roll
.21 / .28extrinsic orientation as a unit quaternion (no gimbal lock at pitch≈90°)
.22 .23boundary points of the valid image circle
The gotcha that hides the whole model: the radial polynomial has five terms, and the fifth lives in field 15, not beside .5–.8. Read only four and the curve is non-monotonic — which is exactly why these coefficients look useless until you find the fifth.

03The lens model — DJI's f-theta

Read straight out of DJI Studio's binary (CameraModel::project). For a camera-frame ray (X,Y,Z):

# incidence angle, then the five-term radial polynomial (raw radians)
theta   = atan2( sqrt(X² + Y²), Z )
theta_d = theta + k1·theta³ + k2·theta⁵ + k3·theta⁷ + k4·theta⁹ + k5·theta¹¹
x', y'  = theta_d · (X, Y) / sqrt(X² + Y²)
# Brown tangential distortion, then the intrinsic matrix
r2      = theta_d²
x''     = x' + 2·p1·x'·y' + p2·(r2 + 2·x'²)
y''     = y' + p1·(r2 + 2·y'²) + 2·p2·x'·y'
u, v    = fx·x'' + cx ,  fy·y'' + cy

No normalisation, no fudge factor. The proof it is the real model, not just a good fit: it out-scores a lookup table built by measuring the lens curve directly against DJI's export — a model carrying form-error cannot beat a direct measurement.

04Stitching a frame

  • Project every output pixel's world direction into each lens (extrinsic quaternion + f-theta) to build a remap.
  • Level to the gravity vector — horizon flat; heading is a free choice for a 360.
  • Field of view = 180° + seam_overlap_ratio·360° = 193.7°, derived from DJI's shipped seam_overlap_ratio (0.038), not tuned.
  • Exposure — the sensors meter and vignette differently. A single gain can't fix a difference that varies across the seam, and a per-pixel field fights parallax; multi-band blending fades it invisibly instead.

05What DJI does that this deliberately doesn't

Matching DJI's exported pixels is not the goal — several of its steps are creative choices for the edit, not a faithful conversion:

  • Colour grading. DJI bakes a look on export. Shot in D-Log-M, that grade belongs in the edit, so the log curve is preserved untouched here.
  • Electronic stabilisation. DJI smooths the camera path (forward-view EIS). Locking the world orientation already stabilises a 360; heavier smoothing re-frames the shot and is the editor's call.
  • Rolling-shutter deroll. DJI warps each frame per-row from the IMU. The data is in the file and it's implemented — but on handheld footage the readout motion is ~1–2° and the skew sub-pixel, so it's off by default. It matters for fast whip-pans.

There is also a fixed ~1.5° offset between the accelerometer's “down” and DJI's world down — a camera↔IMU mount rotation DJI defaults internally and does not store. A gravity-levelled horizon is objectively level, so it isn't chased.
